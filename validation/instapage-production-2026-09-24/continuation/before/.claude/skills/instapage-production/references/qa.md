# QA: fidelity, native authorability and function

QA compares four things and reports where they differ:

1. the approved work packet (the ask);
2. the approved copy (WordSmither, exact version);
3. the approved Figma spec (DesignChamp, exact version);
4. the actual Instapage page (page ID and version), or, before a page exists, the build sheet.

It produces a machine-readable result and a short human report. There is no creative score: production QA does not judge the idea, it checks that the approved idea was built faithfully and natively. Creative judgment stays with DesignChamp and CreativeDirector.

## 1. Statuses

| Status | Meaning |
|---|---|
| **PASS** | Checked, with evidence, and it holds. A check that does not apply passes with evidence beginning "Not applicable:" |
| **FAIL** | Checked, and it does not hold. The owner is named |
| **WARNING** | Holds with a risk or a small deviation the owner must acknowledge. Never blocks publishing |
| **NOT_RUN** | Could not be checked at this stage or without a connection. Says why |

Each check has a **blocking** flag. A FAIL or NOT_RUN on a blocking check blocks publishing. The catalog below sets the flag; QA may not lower it.

## 2. Stages

| Stage | Compared against | Typical NOT_RUN |
|---|---|---|
| **PLAN** | The build sheet, before anything is built | Everything that needs the real page |
| **DRAFT** | The unpublished page, in the editor and in preview | Forms, integrations, scripts, sticky bars (need a published URL) |
| **STAGING** | The page published to a pagedemo URL with the user's OK | None expected |
| **LIVE** | The page at its production URL, right after publishing | None expected; this is the smoke test |

## 3. Check catalog

Owners: DC DesignChamp · WS WordSmither · BM BriefMachine · CD creative-engine-director · PR production (this skill) · US the user or client. Every check is blocking except where marked "no".

### Creative fidelity (CF)

| CF-03 | Imagery is the approved assets, with the specified crops and focal points | DC |
| CF-04 | Visual hierarchy: the specified focal point is seen first; emphasis is where the spec puts it | DC |
| CF-05 | Typography intent: faces, font roles, sizes, weights and heading levels as specified | DC |

| CF-08 | Color: values and their jobs as specified | DC |

## 4. How checks are run

| Evidence source | Used for |
|---|---|
| The build sheet and `ip_check.py plan` | PLAN stage; CF-01, CF-02, NA-02 to NA-07, FN-03, FN-06, GV-01, GV-02, GV-08 as planned |
| `page_export_json` + `page_snapshot_read` | Element types, text, heading levels, links, images, inline CSS and page code, once the JSON paths are recorded (`mcp-and-api.md` §7) |
| The Instapage editor (user signed in, or a production designer) | Block and container settings, mobile layout, visibility, Global Block status, integrations, conversion goals, Scripts & Privacy, the editor test |
| The built-in browser on preview, staging and live URLs | Rendering at each width, links, forms, sticky bars, popups, tags (network requests), cookie bar |
| The copy doc, spec and packet | The reference side of every comparison |

Screenshots taken as evidence are saved under `work/production/qa/<packet>_<check>_<width>_v<NN>.png` when useful. Never record personal data, API keys or unmasked submissions as evidence.

## 5. Machine-readable result

`work/production/<packet>_instapage-qa_v<NN>.json`:

```json
{
  "format": "instapage-qa/1",
  "meta": {
    "client": "<client, as in the packet>",
    "project": "<project>",
    "packet": "<packet ID>",
    "stage": "PLAN | DRAFT | STAGING | LIVE",
    "date": "YYYY-MM-DD",
    "by": "<who ran QA>",
    "page": { "workspace_id": "<id or OPEN>", "page_id": "<id or null>", "name": "<name>", "version": "<v or null>", "url": null },
    "compared": { "packet": "<path>", "copy": "<path, version>", "spec": "<Figma link, version>", "build_sheet": "<path>" }
  },
  "checks": [
    { "id": "CF-01", "status": "PASS", "blocking": true, "owner": "WS", "evidence": "<what was compared, where>" }
  ],
  "blocking_issues": ["<ID>: <one line>"],
  "approvals": {
    "creative": { "by": null, "date": null, "evidence": null },
    "go_ahead": { "by": null, "date": null, "evidence": null }
  },
  "result": { "pass": 0, "fail": 0, "warning": 0, "not_run": 0, "publish_allowed": false }
}
```

Rules the validator enforces (`python3 scripts/ip_check.py qa <file>`):

- Every catalog check appears exactly once, with the catalog's blocking flag and a status from §1.
- PASS, FAIL and WARNING carry evidence; NOT_RUN says why.
- `blocking_issues` lists exactly the blocking checks that are FAIL or NOT_RUN.
- `result` counts match the checks.
- `publish_allowed` is true only when no blocking check is FAIL or NOT_RUN and both approvals have a name, a date and evidence.
- No numeric score anywhere in the file.

## 6. Human report

`work/production/<packet>_instapage-qa_v<NN>.md`, short:

```
INSTAPAGE QA · <client> · <project> · <packet> · <stage> · <date>
PAGE:       <name> · <page ID> · version <v> · <draft / staging URL / live URL>
COMPARED:   packet <…> · copy <…> · spec <…> · build sheet <…>
RESULT:     <n> PASS · <n> FAIL · <n> WARNING · <n> NOT RUN · publish allowed: YES / NO

BLOCKING
- <ID> <check>: <finding> → <owner>
WARNINGS
- <ID>: <finding> → <owner acknowledges>
NOT RUN
- <IDs>: <why, and what would run them>
NEEDS A DECISION
- <constraint reports and proposed exceptions, with who decides>
```

Blocking findings go straight to their owners as constraint reports (SKILL.md). QA does not fix creative problems by changing copy or design.
